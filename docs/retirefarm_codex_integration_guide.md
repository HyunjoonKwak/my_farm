## 0. 받는 Codex에게: 작업 범위와 시작 방법

이 문서를 현재 retirefarm_manager 작업 세션의 구현 요구사항으로 사용하라. 기존 작업과 충돌하지 않도록 먼저 실제 작업 브랜치, git status, AGENTS.md와 적용되는 저장소 지침, 진행 중인 변경을 확인하라. 다른 세션의 변경을 되돌리거나 덮어쓰지 말라. 아래 경로와 구조는 2026-09-14에 GitHub main을 읽고 파악한 내용이므로 현재 체크아웃을 다시 확인하라. 실제 운영 환경에서 기능이 켜져 있거나 데이터가 충분하다는 뜻은 아니다.

우선 짧은 갭 분석과 단계별 계획을 제시한 뒤, 외부 계정 없이 가능한 1단계 구현·테스트를 진행하라. 후속 단계도 안전하게 가능한 범위에서 진행하되, 인증·수집 접근 제한은 우회하지 말고 필요한 설정만 보고하라. 실제 텔레그램 발송, 운영 배포, 운영 DB 마이그레이션, 기존 예약 변경은 사용자 확인 없이 수행하지 말라. 자동 발송·새 예약 기능은 기본 비활성화한다. 이 문서 작성 세션에서는 프로젝트 코드를 수정하지 않았다.

## 1. 사용자 목적

- 평택에서 토경 스마트팜으로 대추방울토마토를 재배하고 온라인 판매하는 생산자를 지원한다.
- 매주 월요일 한국시간 오전 10시 기준으로 도매가격, 재배·기상, 전자상거래·물류, 경쟁 스마트스토어 약 30곳을 분석한다.
- 앱에서 전체 보고서·가격 이력을 보고 텔레그램에서는 핵심 요약·우선 행동 3개·보고서 링크를 받는다.
- 현재 대화 서비스에 별도 주간 브리핑 예약이 존재한다. 2026-09-14 오전 11시 추가 실행도 설정되어 있다. 이 과거 일회 일정을 프로젝트에서 재실행하지 말라. 기존 예약이 프로젝트에 자동 연결되어 있다고 가정하지 말라.
- 참고 판매 조건: 1/2/3/5kg, 배송비 3,500원, 목표마진 15%. 이는 기본 입력값으로 편집 가능하게 두고, 실제 계약 운임·원가·수수료로 확인되지 않은 값은 가정으로 표시한다.

## 2. 핵심 아키텍처 원칙

수집 도구를 하나로 강제하지 않는다. 공통 규칙으로 검증한 데이터와 계산 결과를 프로젝트가 관리하고, 브리핑 작성기는 이를 해석한다.

```text
가락 API 수집 ───────────────┐
허용된 경쟁점 수집/수동 입력 ──┼→ 원본 관측 + 규칙 검증 → DB → 공통 집계
구조화된 외부 조사 가져오기 ──┘                              ↓
기상·정책·물류의 검증된 출처 ───────────────────────→ 브리핑 초안
                                                         ↓ 검토/발행
                                            앱 전체 보고서 + 텔레그램 요약
```

- 경매가격, 온라인 판매가격, 공개 웹 참고시세는 다른 데이터셋으로 유지한다.
- 일별 평균의 단순평균과 거래량 가중평균을 같은 시계열로 이어 붙이지 않는다.
- 검색 스니펫 최저가를 확인되지 않은 3kg 옵션 가격으로 저장하지 않는다.
- 계산은 결정적 코드가 수행한다. AI가 가격·변동률·등급 매핑을 임의 생성하지 않는다.
- 원본 출처, 관측시각, 규칙 버전, 계산 버전, 비교 대상 수, 누락을 추적 가능하게 한다.
- 대화 서비스의 예약 결과를 가져오는 API가 이미 있다고 가정하지 않는다. 초기 연결은 사용자가 내보낸 검증 가능한 JSON/Markdown 가져오기다. 이후 인증된 수신 API 또는 프로젝트 자체 생성 작업은 별도 구현한다.

## 4. 공통 규칙 파일과 계약

버전 관리되는 규칙을 한 곳에 정의하라. 예: src/lib/briefing/rules.ts와 Zod 스키마, 사람이 읽는 docs/briefing-rules.md. 경로는 기존 구조에 맞게 조정 가능하다. 별도 서비스와 교환한다면 같은 규칙의 JSON 직렬화를 제공하라.

필수 계약 필드: schemaVersion, rulesVersion, statisticsVersion, sourceType, sourceUrl, observedAt(UTC ISO), 기준 시간대 Asia/Seoul, 대상 상품/옵션 식별자, 원본 값, 정규화 값, 통화 KRW, 검증 상태, 누락 사유.

규칙 변경 시 이전 관측치를 덮어쓰지 않는다. 재계산 결과에는 새 계산 버전과 입력 관측 식별자를 남긴다. 보고서는 해당 발행 당시 입력·범위를 재현할 수 있어야 한다.

## 5. 도매가격 집계 규칙 v1

아래 기간 규칙은 이번 구현을 위한 제안 기본값이며 기존 웹 보고서의 계산 기준을 소급해 확정하는 것이 아니다.

- 보고 대상 주: 실행일 직전 완료된 월요일 00:00~다음 월요일 00:00, KST 반개구간.
- 전주: 대상 주 바로 앞의 동일 7일 구간.
- 최근 4주: 대상 주를 포함한 완료된 4주. 화면·보고서에 실제 시작일과 종료일을 표시.
- 월요일 당일 가격은 별도 최신 참고값이며 완료된 주간 평균에 혼합하지 않는다.
- 대추방울과 일반 방울을 구분한다. 실제 품목/품종 명칭을 확인하고 검증되지 않은 별칭을 자동 합치지 않는다.
- 기본 그룹: 법인·품종·등급·포장단위. 산지 필터를 적용하면 모든 비교기간에 동일 적용.
- 동일 포장단위 그룹의 평균: sum(price * quantity) / sum(quantity).
- kg당 가격: 중량을 명확하게 해석할 수 있는 거래만 sum(price * quantity) / sum(packageKg * quantity).
- 3kg 환산값: 반올림 전 kg당 값 * 3. 실제 3kg 거래 평균과 구분.
- 4주 평균은 원거래를 다시 합산한 가중평균. 반올림된 일/주 평균을 다시 평균하지 않는다.
- 거래건수, 수량의 단위, 총중량, 제외건수, 수집 상태를 함께 반환한다. quantity의 원본 API 의미를 검증하기 전 총수량을 kg으로 표현하지 않는다.
- 가격·수량이 0 이하이거나 비정상인 거래는 평균에서 제외하고 이유·건수를 보고한다. 단위 미확인 거래는 kg 환산에서만 제외할 수 있다.
- 전기 값이 없거나 0이면 변동률은 null. 결측·수집 실패·휴장은 구분하며 무거래만으로 휴장을 추정하지 않는다.
- 법인 합산값은 별도 그룹으로 명시한다. 법인·산지 구성 변화가 평균에 영향을 줄 수 있음을 표시한다.
- DB 전체 집계 또는 안정적 페이지 처리를 사용하여 20,000건 제한 영향을 없앤다. 최신 거래 일부만으로 전체 평균이라고 표시하지 않는다.
- 공개 웹 시세는 sourceType을 달리하고 참고/교차 검증으로만 표시한다. API 장애 시 자동 대체하여 같은 시계열에 연결하지 않는다.

## 6. 스마트스토어 30곳 선정과 추적

### 6.1 순위와 고정 패널

- 최초 목표: 네이버 쇼핑 '대추방울토마토', 기본 정렬, 광고 제외 상위 노출의 서로 다른 스마트스토어 약 30곳.
- 검색경로·검색어·정렬·확인시각·로그인/개인화 여부를 가능한 범위에서 기록한다. 검색 노출은 실제 판매량 순위가 아니다.
- 실제 그 조건의 순위를 확인할 수 없으면 일반 검색/API 결과를 동일 순위로 가장하지 않는다. 대체 후보 목록은 '가격 참고 표본'으로 구분하여 사용자가 패널 확정 가능하게 한다.
- 고정 패널은 동일 상품·옵션의 가격 추이용, 주간 상위 노출 목록은 진입·이탈 동향용이다. 서로 다른 통계로 제공한다.
- 패널 교체는 사유와 효력일 기록. 품절·상품 삭제를 조용히 다른 상품으로 대체하지 않는다.
- 일반 신선 대추방울을 기본군으로 한다. 스테비아·가공품 제외. 유기농/인증·선물용·못난이·등급 차이는 분리한다.

### 6.2 가격 관측

- 식별: storeId, productId, optionId(없으면 미확인), 상품 URL, 옵션 원문, 중량, 등급/크기, 산지, 인증.
- 금액: 표시가, 즉시할인가, 배송비, 무료배송 조건, 제주 추가운임, 쿠폰 금액/조건/유효기간을 별도 저장.
- 기본 가격은 단일 해당 옵션 구매 시 비회원/일반 구매자에게 확인 가능한 즉시 구매가 + 기본 배송비. 다운로드 쿠폰 등은 확인된 조건과 별도 시나리오로 표시한다.
- 회원/첫구매/카드/앱/구매금액 조건부 할인과 적립금을 기본가격에서 임의 차감하지 않는다.
- 가격 변동 원인을 상품가격/쿠폰/배송비/구성 변경으로 분해한다.
- 1/2/3/5kg 옵션을 확인 가능한 범위에서 조사. 상품가 kg환산과 배송비 포함 실제 구매총액을 별도 필드로 둔다. 배송비를 중량 비례 환산하지 않는다.
- 배송지역을 고정된 기본 배송권역으로 정의하고 표시한다. 개인 상세주소는 수집하지 않는다. 제주 추가운임은 별도 비교한다.
- 품절, 검색정보만 확인, 옵션 미확인, 접근 실패, 배송비 미확인은 상태값이다. 0원으로 대체하거나 과거값을 현재 관측으로 복제하지 않는다.
- 관측된 과거 데이터만 비교한다. 최초 실행은 기준선이다. 수집되지 않은 과거 가격을 만들어 채우지 않는다.

### 6.3 통계와 전략

- 동일 상품군·옵션·중량·가격조건의 중앙값/범위/표본 수를 표시한다.
- 주간 변동은 두 시점 모두 유효한 동일 상품 쌍으로 계산한다. 전체 유효 표본 수와 동일 비교 가능 표본 수를 구분한다.
- 신선도 기준(예: 24시간)은 규칙으로 명시하고 오래된 값은 stale로 분리한다. 이번 주 가격은 주간 한 시점 관측이지 주간 전체 평균이 아니다.
- 전략: 직송·토경·산지·당도표시·인증·선별·수확/발송일·포장·묶음·구독·쿠폰·리뷰 활용·상세페이지 메시지. 전략 근거 URL/확인시각을 저장한다.
- 광고 문구의 주장은 '판매자 표시'로 분리한다. 판매량이나 전략 효과를 근거 없이 추정하지 않는다.

## 7. 브리핑 내용과 데이터 모델 제안

보고서는 한국어 존댓말, 최근 일주일의 중대한 변화 중심으로 작성한다.
1. 도매가격과 변동 원인: 확인된 사실과 해석을 분리.
2. 평택/중부권 기상·병해충·토양·관수·양분·에너지·연구·정책·지원사업.
3. 네이버 등 수수료·광고·표시·정산·규제 및 한진 등 운임·제주·포장·신선물류.
4. 경쟁점 약 30곳 가격·전략·추이, 실제 조사 수와 누락.
각 항목: 무엇이 바뀌었는지 / 왜 중요한지 / 고려할 행동. 끝에 우선 행동 3개. 중대한 변화 없음과 자료 확인 불가를 구분한다. 발표일·시행일·관측일을 구분하고 출처 링크를 붙인다.

Prisma 확장 후보(이름은 제안):
- CompetitorStore, CompetitorProduct/Option: 고정 식별과 패널 상태.
- CompetitorObservation: 관측시각·가격 구성·조건·상태·출처·규칙 버전. append-only.
- SearchSnapshot/PanelMembership: 노출 순위와 고정 패널의 이력 분리.
- WeeklyBriefing: 사용자 소유권, 기간, 버전, 상태(DRAFT/PUBLISHED), 본문·요약·입력 snapshot·출처.
- BriefingRun: 주차/작업종류/사용자 기준 중복 방지, 상태, lease, 재시도.
- NotificationDelivery: 브리핑/채널/수신처/버전별 고유키, 상태·시도·외부 메시지 ID.
- 사용자 TelegramConnection: 검증된 수신처, opt-in, 연결 해제. 토큰은 일반 사용자 조회 응답에 포함하지 않는다.

외부 가져오기는 Markdown 본문만 받는 경우와 구조화된 관측 JSON을 받는 경우를 구분한다. 본문 속 표를 근거 없이 DB 관측으로 자동 승격하지 않는다. JSON은 버전·Zod·크기 제한·중복키·금액·URL·시간 검증 후 미리보기와 반영을 제공한다. 제공된 URL을 서버가 자동 방문하면 SSRF 방어가 필요하므로 초기 단계에서는 링크 저장만 권장한다. HTML/Markdown 렌더링은 XSS 방지한다.

## 8. 텔레그램과 실행 안전성

- src/lib/services/telegram.ts 등 서버 전용 어댑터. 실제 Bot API 사양은 구현 시 공식 문서 https://core.telegram.org/bots/api 에서 재확인.
- 서버 비밀 설정에 TELEGRAM_BOT_TOKEN, 수신 연결은 사용자별로 관리. 토큰을 NEXT_PUBLIC 변수, Git, 로그, URL 에러 덤프에 노출하지 않는다.
- 실제 수신 대상 소유/접근과 동의를 확인한 뒤 연결. 테스트 전송 버튼도 명시적인 사용자 액션과 인증 필요.
- 기본 메시지: 날짜·한줄 판단·가격 요약·행동 3개·로그인이 필요한 앱 보고서 링크. 긴 전체표는 앱에서 제공한다.
- 요청 타임아웃, 429 retry_after, 5xx의 제한된 백오프, 인증/수신권한 실패의 재시도 중단을 처리한다.
- 전달 이력을 DB에 저장해 같은 보고서 재발행·재시작 시 중복 발송을 줄인다. 네트워크 타임아웃으로 성공 여부 불명인 경우 무조건 재전송하지 않는다. 외부 API 특성상 엄밀한 exactly-once를 보장한다고 주장하지 않는다.
- 주간 job은 Asia/Seoul 기준. 오전 10시 생성 시작인지 발송 완료 목표인지 화면에 명시한다. 초기값은 10시 실행 시작, 완료 후 전송.
- 앱 내 cron만 사용할 경우 상시 실행되는 프로세스가 필요하다. 실제 Docker/서버리스 배포를 확인하고 적절한 runner를 선택한다.
- 여러 프로세스·수동 실행·예약 실행 동시 호출에 대비한 DB 고유키와 lease를 사용한다. 프로세스 내 Set만으로 중복 방지를 끝내지 않는다.
- 복구 실행은 동일 주차 중복 방지 및 수집기간 고정. 실행이 늦었다고 미래/이번 주 데이터를 과거 보고서에 섞지 않는다.
- 기존 ChatGPT 예약과 새 프로젝트 예약을 둘 다 활성화해 중복 발송하지 않는다. 연결 방식과 운영 주체를 사용자가 확인한 후 전환한다.

## 9. 가격 의사결정 표시

경락가를 생산원가로 단정하지 않는다. 경매 판매 기회비용으로 활용한다면 위탁수수료·시장 운송비 등을 반영한 순수취액인지 명시한다. 온라인 채널 비교는 포장·배송·판매/결제수수료·할인·예상 손실을 분리한다.

목표마진을 매출 대비 비율로 정의한다면 예시 공식은 P = 고정원가합 / (1 - 변동수수료율 - 목표마진율). 단, 수수료 부과 기준·배송비 별도 수납 등에 따라 달라지므로 확인되지 않은 조건에서 보편적 판매하한으로 표시하지 않는다. 분모 <= 0은 오류. 가격 자동 변경은 이 프로젝트 범위에 포함하지 않는다.

## 10. 구현 단계와 완료 기준

### 1단계: 공통 규칙·브리핑 보관·수동 가져오기·텔레그램 기반

현재 코드 재검토 → 공통 스키마/규칙 → 브리핑 DB/인증 API/목록·상세 화면 → JSON 검증·미리보기 가져오기 → 텔레그램 어댑터·발송이력·dry-run 구현. 실제 전송/자동 발행은 OFF.
완료: 샘플 관측과 보고서를 임시 DB에 저장·조회하고, 잘못된 JSON을 거부하며, mock 전송과 중복 방지 테스트 통과. 토큰 없이도 기능 검증 가능.

### 2단계: 기존 도매 데이터의 정확한 주간 집계

법인/품종/등급/중량/기간을 고정한 전체 거래 집계 API와 보고서 입력 생성. 수집 상태·제외건수·기준 변경 표시. 기존 시세 화면·수집 작업 회귀 방지.

### 3단계: 경쟁점 패널·관측 이력

우선 사용자 확정 패널 및 검증된 수동/JSON 관측으로 추이 구현. 허용된 수집 경로가 검증될 때 어댑터 연결. 실제 접근 없이 30곳 자동수집 완료를 주장하지 않는다. 네이버 공식 API를 검토한다면 검색 필드·정렬이 소비자 화면/옵션/쿠폰을 재현하는지 확인하고 동일하다고 가정하지 않는다.

### 4단계: 자동 조사·생성·예약 발송

현재 선택한 AI/검색 제공자와 비용·접근권한을 확인한 후 도입. 제공자가 미정이면 어댑터와 수동 입력으로 유지하며 유료 계정을 임의 선택하지 않는다. 수치 계산은 기존 집계 결과만 이용. 출처 부족 시 초안/부분 보고서 처리. 사용자 승인 후 하나의 예약 주체에서 실제 발송 시작.

## 11. 필수 테스트

- KST 월요일 경계, UTC 서버, 월/연도 변경, 대상 주와 직전 4주 반개구간.
- 동일 그룹 거래량 가중평균, 원거래 4주 집계, 반올림, 3kg 실거래/환산 구분.
- 단위 불명, 0/음수 수량·가격, 결측·부분 수집, 20,000건 초과 데이터에서 절단 없는 통계.
- 품목/법인/등급/산지 필터가 비교기간 모두 동일 적용.
- 1kg 검색 최저가와 3kg 옵션 불일치, 배송비 미확인, 제주, 무료배송 문턱, 조건부 쿠폰·적립금.
- 품절·옵션 교체·패널 진입/이탈이 순수 가격 변동으로 집계되지 않음.
- 최초 관측에서 전주/4주 추이 없음, stale 구분, 동일 비교쌍 수 표시.
- 가져오기 중복/잘못된 버전/과도한 크기/악성 HTML/타인 보고서 접근 거부.
- 텔레그램 mock 성공·429·5xx·권한 실패·타임아웃, 재시작·동시 실행·중복 발송 방지.
- 기존 수집·복구·백업·로그인·시세 화면 회귀 테스트.

저장소에 존재하는 명령을 확인하고 npm run typecheck, npm run lint, npm test, npm run build 실행 결과를 보고하라. 실패를 숨기지 말고 기존 실패와 신규 회귀를 구분하라. 임시 테스트 DB만 사용한다. 마이그레이션은 개발용으로 작성하되 운영 DB에 db push로 우회 적용하지 않는다.

## 12. Codex의 최종 인계 항목

1. 구현한 단계와 남은 단계, 변경 파일 목록.
2. 확정한 규칙·스키마 버전 및 샘플 입력/출력(가상 데이터 표시).
3. 테스트 명령별 결과와 검증하지 못한 운영 항목.
4. 필요한 환경변수 이름만 제시(비밀값 제외).
5. 마이그레이션·백업·롤백과 배포 절차, 실제 발송 활성화 전 체크리스트.
6. 실제 경쟁점 확보 수, 접근 제한, 생성 제공자 미설정 등 외부 의존성.
7. 기존 예약은 변경하지 않았다는 사실 또는 사용자 승인으로 변경한 정확한 범위.

작업 개시 요약: 현재 변경을 보존하면서 공통 규칙과 1단계부터 구현하라. 이미 구현된 기능이 있다면 중복 생성하지 말고 요구사항 대비 차이만 보완하라. 운영 배포와 실제 전송은 별도 승인 전까지 하지 말라.
